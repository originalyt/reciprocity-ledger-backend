# 人情往来记账系统需求文档 V1.1

## 1. 需求背景
本系统用于记录“人情往来”场景下的礼金收送情况，核心目标是围绕“联系人 + 事件 + 收礼/送礼记录”形成可查询、可统计、可追溯的人情台账。

本系统不是普通流水账，不记录日常消费、账户余额、支付渠道或财务收支明细。

## 2. 产品目标
1. 记录本人与联系人之间在具体事件上的礼金往来。
2. 支持按联系人、事件、时间范围、事件类型等多维度查询。
3. 支持统计某时间段内的收礼总额、送礼总额及时间线。
4. 支持查看与某个联系人的历史往来时间线。
5. 支持基于历史记录提供回礼参考。
6. 支持识别并标记“同类事件下是否已回礼/已收礼”，并允许人工取消。
7. 用户端以 APP 为主要使用终端，能力设计优先满足移动端使用习惯。

## 3. 使用范围
1. 当前版本仅面向单用户使用。
2. 用户端主要通过 APP 使用，后端提供与 APP 配套的接口能力。
3. 不考虑多人协作、多租户、家庭共享账本。
4. 当前版本仅记录金额型人情，不记录礼品、物品、宴请、帮忙办事等非金额往来。
5. 不按家庭维度管理，以主要联系人为准。

## 4. 术语定义
1. 联系人：与本人发生人情往来的对象，如亲戚、朋友、同事。
2. 事件：人情发生的背景，如结婚、满月、乔迁、白事等。
3. 人情记录：本人与某联系人在某个事件上的一笔礼金记录。
4. 收礼：从本人视角出发，表示本人收到对方礼金。
5. 送礼：从本人视角出发，表示本人向对方送出礼金。
6. 同事件闭环：指本人与同一联系人在同一事件类型上形成了“对向往来”。例如“对方结婚我送礼”与“我结婚对方送礼”可视为一次闭环。
7. 回礼参考：基于历史同类事件和历史往来记录展示参考信息，不直接给出建议金额。

## 5. 核心业务对象

### 5.1 联系人
联系人为必填项。

建议字段：
1. 联系人姓名
2. 别名
3. 称呼
4. 手机号
5. 关系类型
6. 备注

关系类型建议预置：
1. 亲戚
2. 朋友
3. 同事
4. 同学
5. 邻居
6. 其他

说明：
1. 不提供地址字段。
2. 不按家庭维度管理。

### 5.2 事件
事件为必填项，采用公共事件库统一管理。

建议字段：
1. 事件名称
2. 事件类型
3. 事件日期
4. 事件备注

事件类型首期建议预置：
1. 结婚
2. 生子
3. 满月
4. 周岁
5. 乔迁
6. 生日
7. 白事
8. 升学
9. 节日往来
10. 其他

说明：
1. 录入人情记录时必须选择事件。
2. 同一个联系人可以关联多个不同事件记录。
3. 同一事件可以关联多个联系人记录。
4. 为支持闭环判断，事件库中的事件需要能够区分事件归属对象，但该信息属于事件自身属性，不作为新增人情记录时的额外录入项。

### 5.3 人情记录
人情记录为系统核心数据。

建议字段：
1. 记录日期
2. 联系人
3. 事件
4. 收礼/送礼
5. 金额
6. 备注
7. 同类事件闭环标识
8. 闭环标识是否手动取消
9. 回礼参考信息

说明：
1. 新增记录时必须手动选择“收礼”或“送礼”。
2. 收礼/送礼始终从本人视角定义。
3. 一条记录只能对应一个联系人和一个事件。
4. 一条记录不可与其他记录合并。
5. 人情记录不允许删除，如录入有误，通过编辑修正。

## 6. 业务规则

### 6.1 录入规则
1. 联系人为必填。
2. 事件为必填。
3. 收礼/送礼为必填。
4. 金额为必填，且必须为正数。
5. 当前版本只记录金额，不支持非金额型人情。
6. 一条记录只对应一笔独立往来，不做拆分合并。

### 6.2 收送规则
1. 收礼表示本人收到对方礼金。
2. 送礼表示本人给对方送出礼金。
3. 所有统计、查询、时间线均以本人视角解释收礼/送礼。

### 6.3 公共事件库规则
1. 事件通过公共事件库维护。
2. 人情记录必须关联事件库中的一个事件。
3. 同一联系人允许关联多个事件。
4. 同一事件允许被多条人情记录引用。

### 6.4 同类事件闭环规则
系统需要对“是否已回礼/已收礼”进行标识，且允许人工取消。

闭环识别原则：
1. 联系人为同一人。
2. 事件类型相同。
3. 两条记录在本人视角下方向相反，一条为收礼，一条为送礼。
4. 两条记录分别对应双方各自主体事件。
5. 满足以上条件时，可形成闭环候选。

示例：
1. 张三结婚，我送礼 500。
2. 我结婚，张三送礼 500。
3. 这两条记录在“结婚”这一事件类型下可形成闭环。

闭环状态建议：
1. 未闭环
2. 已闭环
3. 已手动取消闭环
4. 已手动标记闭环

说明：
1. 系统可自动识别闭环候选。
2. 用户可以手动取消或修正闭环状态。
3. 闭环标识的优先级高于回礼建议。

### 6.5 回礼参考规则
1. 系统只展示历史参考，不直接计算建议金额。
2. 回礼参考应尽量围绕“同一联系人 + 同一事件类型”展示。
3. 回礼参考可展示以下内容：
   1. 对方历史在同类事件中给过我的金额
   2. 我历史在同类事件中给过对方的金额
   3. 双方历史总收礼金额
   4. 双方历史总送礼金额
   5. 最近一次同类事件往来金额
   6. 是否存在未闭环记录

## 7. 功能需求

### 7.1 联系人管理
1. 新增联系人
2. 编辑联系人
3. 查看联系人详情
4. 联系人列表查询
5. 按姓名、别名、手机号、关系类型筛选

### 7.2 事件管理
1. 新增事件
2. 编辑事件
3. 查看事件详情
4. 事件列表查询
5. 按事件类型、时间范围筛选
6. 从公共事件库选择事件用于录入记录

### 7.3 人情记录管理
1. 新增人情记录
2. 编辑人情记录
3. 查看人情记录详情
4. 按联系人、事件、方向、时间范围查询记录
5. 查看闭环状态
6. 手动取消闭环状态
7. 手动标记闭环状态
8. 查看回礼参考信息

说明：
1. V1 不支持删除人情记录。
2. 录入错误通过编辑修正。

### 7.4 查询与统计
系统至少需要支持以下查询能力：

1. 某时间段内我的收礼总额
2. 某时间段内我的送礼总额
3. 某时间段内我的收送对比
4. 与某个联系人的收礼送礼时间线
5. 我个人在某时间段内的收礼送礼时间线
6. 某事件下的全部往来明细
7. 按联系人维度汇总收礼总额、送礼总额
8. 按事件类型维度汇总收礼总额、送礼总额
9. 查询存在未闭环记录的联系人或事件
10. 查询某联系人在某类事件上的历史往来情况

## 8. APP 页面视图建议

### 8.1 APP 首页
建议展示：
1. 近期人情记录
2. 某时间段收礼总额
3. 某时间段送礼总额
4. 待关注的未闭环记录
5. 近期事件

### 8.2 联系人详情页
建议展示：
1. 联系人基本信息
2. 历史人情记录
3. 收送汇总
4. 与该联系人的时间线
5. 同类事件回礼参考
6. 未闭环记录

### 8.3 事件详情页
建议展示：
1. 事件基本信息
2. 该事件下的全部记录
3. 该事件下的统计信息
4. 涉及的联系人列表

### 8.4 时间线页面
建议展示：
1. 本人某时间段的收礼送礼时间线
2. 某联系人的收礼送礼时间线

### 8.5 APP 交互要求
1. 录入记录时应减少输入步骤，优先使用选择器、预置项和快捷录入。
2. 常用查询应支持按时间段、联系人、事件类型快速筛选。
3. 金额、收礼、送礼、闭环状态等关键信息应在列表中清晰展示。
4. 适合移动端单手操作，重点功能应尽量在 2 到 3 次点击内完成。

## 9. 统计口径
1. 收礼总额：方向为“收礼”的金额合计。
2. 送礼总额：方向为“送礼”的金额合计。
3. 净往来额：收礼总额减送礼总额。
4. 联系人汇总：按联系人聚合收礼、送礼、净往来额。
5. 时间线默认按记录日期排序，支持升序和倒序。
6. 统计默认按记录日期进行。

## 10. 非功能要求
1. 数据展示应清晰区分“收礼”和“送礼”，避免用户理解混乱。
2. 历史记录应保持稳定可追溯，不允许因删除导致统计失真。
3. 闭环识别结果必须支持人工修正，避免系统误判影响使用。
4. 查询和统计应支持常用时间范围筛选，如本月、本年、自定义区间。
5. 用户端以 APP 为主，接口设计和响应字段应优先考虑移动端展示与加载效率。

## 11. V1 暂不纳入范围
1. 家庭维度管理
2. 多用户协作
3. 非金额型人情记录
4. 自动给出建议回礼金额
5. 地址信息
6. 财务账户、支付方式、流水账功能
7. 复杂关系网络分析

## 12. 结论
V1 的核心是把“联系人、事件、人情记录、闭环标识、历史参考、时间线与统计”这几类能力先做扎实。

系统重点不在财务记账，而在“人情往来的历史管理、闭环跟踪和回礼参考”。
