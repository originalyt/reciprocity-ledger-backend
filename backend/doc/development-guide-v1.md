# 人情往来记账系统开发指导文档 V1.0

## 1. 文档目标
本文档用于指导后端 V1 开发落地，目标不是重复需求，而是把“需求如何拆成代码和数据库实现”讲清楚。

适用范围：
1. Spring Boot 后端开发
2. PostgreSQL 数据库建模与脚本落地
3. APP 端接口协作
4. V1 版本功能优先级控制

本文档以以下已有文档为基础：
1. `renqing-requirements-v1.md`
2. `interface-list-v1.md`
3. `database-schema-v1.md`
4. `sql/baseline.sql`

## 2. 开发目标
V1 要先完成一个可闭环的最小可用版本，优先保证以下能力可用：
1. 联系人管理
2. 公共事件管理
3. 收礼/送礼记录管理
4. 时间线查询
5. 同类事件闭环识别与手工修正
6. 回礼历史参考
7. 统计总览

V1 不追求：
1. 智能推荐具体回礼金额
2. 多用户体系
3. 导入导出
4. 复杂搜索
5. 删除能力

## 3. 推荐分层设计

### 3.1 包结构建议
建议按业务域拆包，不按技术层级单独堆砌公共目录。

建议包结构：
1. `com.reciprocityledger.backend.common`
2. `com.reciprocityledger.backend.contact`
3. `com.reciprocityledger.backend.event`
4. `com.reciprocityledger.backend.record`
5. `com.reciprocityledger.backend.reciprocity`
6. `com.reciprocityledger.backend.stats`
7. `com.reciprocityledger.backend.home`
8. `com.reciprocityledger.backend.dict`

每个业务包内建议包含：
1. `controller`
2. `service`
3. `mapper`
4. `model` 或 `entity`
5. `dto`

### 3.2 Controller 建议
建议至少包含以下控制器：
1. `HomeController`
2. `ContactController`
3. `EventController`
4. `RecordController`
5. `ReciprocityController`
6. `StatsController`
7. `DictController`

说明：
1. 所有接口统一使用 `POST`。
2. 所有入参统一用请求对象。
3. 所有返回统一用响应对象，不直接返回简单类型。

### 3.3 Service 建议
建议每个业务域拆分应用服务，避免把所有逻辑塞进一个 service。

建议核心服务：
1. `ContactService`
2. `EventService`
3. `GiftRecordService`
4. `ReciprocityMatchService`
5. `HistoryReferenceService`
6. `StatsService`
7. `HomeService`

职责建议：
1. `GiftRecordService` 负责新增、编辑、详情、分页和时间线。
2. `ReciprocityMatchService` 负责自动识别、手工确认、手工取消闭环。
3. `HistoryReferenceService` 负责按联系人 + 事件类型提供历史参考。
4. `StatsService` 负责统计聚合查询，不在 Controller 中拼 SQL。

## 4. 核心数据模型落地说明

### 4.1 联系人表 `rl_contact`
职责：维护主要往来对象。

实现要点：
1. 姓名必填。
2. 手机号可选，但如果填写必须做格式校验。
3. 联系人不做物理删除，必要时可扩展状态字段做停用。
4. 列表查询支持姓名、别名、手机号模糊搜索。

### 4.2 事件类型表 `rl_event_type`
职责：统一事件类型口径，避免前后端出现字符串不一致。

实现要点：
1. V1 直接用预置字典初始化。
2. 新增事件时，只允许选择启用状态的事件类型。
3. 查询统计时按 `type_code` 或 `event_type_id` 做口径统一。

### 4.3 事件表 `rl_event`
职责：维护公共事件库。

实现要点：
1. 人情记录必须关联事件，不能直接只存事件类型。
2. `event_owner_type` 是闭环判断的关键字段。
3. 当 `event_owner_type = CONTACT` 时，`owner_contact_id` 必填。
4. 当 `event_owner_type = SELF` 时，`owner_contact_id` 为空。
5. 事件不允许删除，编辑时也要避免破坏历史闭环关系。

### 4.4 人情记录表 `rl_gift_record`
职责：保存每一笔收礼或送礼明细。

实现要点：
1. `direction` 从本人视角定义，只能为 `RECEIVE` 或 `SEND`。
2. 一条记录只对应一个联系人和一个事件。
3. 金额必须大于 0。
4. 记录不允许删除，录错通过编辑修正。
5. 闭环状态直接保存在记录表，便于列表和时间线查询。

### 4.5 闭环匹配表 `rl_reciprocity_match`
职责：保存两条记录之间的闭环关系。

实现要点：
1. 自动识别和手工确认都写入该表。
2. 取消闭环不删除数据，只修改为 `CANCELED`。
3. 一条有效记录最多对应一个有效闭环。
4. 取消时同步回写两条记录状态。

## 5. 关键业务规则转代码说明

### 5.1 收礼/送礼口径
必须统一使用本人视角：
1. `RECEIVE`：本人收到礼金
2. `SEND`：本人送出礼金

为什么这样做：
1. 查询统计时不需要再做方向翻译。
2. APP 展示口径一致。
3. 闭环匹配逻辑更稳定。

### 5.2 事件归属口径
事件必须具备归属信息：
1. `SELF`：本人事件
2. `CONTACT`：联系人事件

为什么这样做：
1. 仅依赖“收礼/送礼 + 事件类型”无法稳定判断闭环。
2. 例如“张三结婚我送礼”和“我结婚张三送礼”，必须知道事件分别属于谁，才能识别这是一组闭环候选。

### 5.3 闭环识别规则
自动识别建议满足以下条件：
1. 联系人相同。
2. 事件类型相同。
3. 收送方向相反。
4. 一条记录对应联系人事件，另一条记录对应本人事件。
5. 两条记录都没有被其他有效闭环占用。

自动识别只产生“候选闭环并落库”，不做复杂金额计算。

### 5.4 手工确认闭环
手工确认时必须校验：
1. 两条记录都存在。
2. 两条记录联系人相同。
3. 两条记录事件类型相同。
4. 两条记录方向相反。
5. 两条记录当前没有参与其他有效闭环。

### 5.5 手工取消闭环
手工取消时必须保证：
1. 匹配关系存在且当前状态为有效。
2. 写入取消原因。
3. 同步更新两条记录的闭环状态。
4. 如果后续重新识别，可再次建立新的闭环记录。

### 5.6 回礼历史参考
V1 只返回参考信息，不计算建议金额。

建议返回内容：
1. 同类型历史收礼总额
2. 同类型历史送礼总额
3. 最近一次同类型记录
4. 未闭环记录数量

为什么只做参考：
1. 人情往来金额判断受地区、关系、年份影响较大。
2. V1 先把历史数据查准，比“智能建议”更重要。

## 6. 推荐开发顺序

### 6.1 第一阶段：字典和基础数据
1. 建表并初始化 `rl_event_type`
2. 完成联系人模块
3. 完成事件模块

交付目标：
1. 可以维护联系人
2. 可以维护公共事件
3. APP 能正常选择事件和联系人

### 6.2 第二阶段：人情记录核心闭环
1. 完成人情记录新增
2. 完成人情记录编辑
3. 完成人情记录详情和分页
4. 完成本人时间线
5. 完成联系人时间线

交付目标：
1. 可以完整录入收礼/送礼数据
2. 可以查看基础时间线和筛选结果

### 6.3 第三阶段：闭环识别与手工修正
1. 完成自动闭环识别服务
2. 完成闭环列表
3. 完成闭环详情
4. 完成手工确认闭环
5. 完成手工取消闭环
6. 完成回礼历史参考

交付目标：
1. 能识别同类事件往来闭环
2. 能人工修正识别结果

### 6.4 第四阶段：统计与首页聚合
1. 完成首页概览
2. 完成统计总览
3. 完成按联系人统计
4. 完成按事件类型统计

交付目标：
1. APP 首页可以直接展示核心数字
2. 统计页支持常用分析场景

## 7. 事务边界建议
以下方法必须加事务：
1. 新增人情记录
2. 编辑人情记录
3. 手工确认闭环
4. 手工取消闭环
5. 自动识别闭环

原因：
1. 这些操作会同时改动记录表和闭环表。
2. 如果只更新一部分，会导致状态和关系不一致。

## 8. 接口实现注意事项

### 8.1 请求对象与响应对象
建议每个接口单独定义 DTO，不要多个接口共用一个大而全对象。

为什么这样做：
1. 避免后续字段演化互相污染。
2. 入参校验更清晰。
3. APP 联调时更容易定位问题。

### 8.2 参数校验
建议使用 Spring Validation。

重点校验：
1. ID 不能为空
2. 金额大于 0
3. 日期不能为空
4. 枚举值必须在允许范围内
5. 联系人事件时必须带 `ownerContactId`

### 8.3 返回对象设计
建议列表项直接返回前端需要展示的关键信息，不要让 APP 二次拼装过多字段。

例如记录列表项建议直接返回：
1. 联系人姓名
2. 事件名称
3. 事件类型名称
4. 收送方向
5. 金额
6. 记录日期
7. 闭环状态

## 9. Mapper 与 SQL 编写建议

### 9.1 Mapper 职责
1. Mapper 只做数据读写。
2. 复杂业务判断放在 Service。
3. 统计 SQL 可以单独放查询 Mapper，避免普通 CRUD Mapper 过重。

### 9.2 SQL 风格建议
1. 列名、别名保持统一可读。
2. 列表查询尽量显式写字段，不要盲目 `select *`。
3. 时间线和统计 SQL 要统一筛选条件，防止列表和汇总口径不一致。

### 9.3 统计查询建议
统计类查询推荐直接基于 `rl_gift_record` 聚合，必要时关联：
1. `rl_contact`
2. `rl_event`
3. `rl_event_type`

## 10. 可能的易错点

### 10.1 只按事件类型做闭环匹配
这是最容易出错的地方。

风险：
1. 会把同一联系人下不相关的两条记录错误识别成闭环。
2. 缺少事件归属信息时，系统不知道“是谁的事”。

### 10.2 编辑记录后不重算闭环
风险：
1. 用户修改联系人、事件、方向、金额后，原闭环关系可能失效。
2. 如果不重新校验，会留下脏数据。

建议：
1. 记录编辑后，先解除旧闭环，再重新识别。

### 10.3 直接删除数据
风险：
1. 时间线缺口
2. 统计失真
3. 闭环关系断裂

因此 V1 不实现删除。

### 10.4 APP 列表字段不足
风险：
1. 前端被迫二次请求补字段。
2. 首屏性能差。

建议：
1. 列表接口一次返回足够展示的信息。

## 11. 测试建议

### 11.1 单元测试重点
1. 联系人新增和编辑参数校验
2. 事件新增和编辑参数校验
3. 人情记录新增和编辑逻辑
4. 自动闭环识别逻辑
5. 手工确认和取消闭环逻辑
6. 统计结果口径

### 11.2 集成测试重点
1. 新增联系人 -> 新增事件 -> 新增记录 -> 查询详情
2. 联系人事件送礼 + 本人事件收礼 -> 自动识别闭环
3. 手工取消闭环后 -> 状态回退
4. 编辑记录后 -> 闭环重新识别

### 11.3 边界测试重点
1. 同一联系人多个同类型事件
2. 同一联系人同一天多条记录
3. 只有收礼没有送礼
4. 只有送礼没有收礼
5. 金额相同但事件不同

## 13. 当前建议的开发优先级
P0：
1. 联系人管理
2. 事件管理
3. 人情记录管理

5. 自动闭环识别

8. 统计总览

P1：
1. 按联系人统计
2. 按事件类型统计

P2：
1. 导入导出
2. 搜索增强
3. 更复杂的推荐逻辑

## 14. 总结
V1 的开发重点不是把表和接口铺满，而是先把“记录准、查得出、闭环稳、统计口径统一”这四件事做好。

如果开发过程中需要在复杂度和交付速度之间取舍，优先级应始终是：
1. 记录准确
2. 闭环准确
3. 查询准确
4. 统计准确
5. 页面体验优化
